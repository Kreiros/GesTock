3. LOS TRES ENDPOINTS
--------------------------------------------------------------------------------

El frontend ya llama a estas direcciones exactas. Si cambias alguna, avisame y
la ajusto.


3.1  POST /api/v1/auth/login

     recibe:
       { "tenant_id": "...", "email": "admin@gestock.cl", "password": "..." }

     responde 200:
       {
         "success": true,
         "data": {
           "token": "<jwt>",
           "usuario": {
             "id": "...",
             "tenant_id": "...",
             "nombre": "Admin Demo",
             "email": "admin@gestock.cl",
             "rol": "admin"
           }
         }
       }

     401 si el correo no existe o la clave no coincide.

     Importante: que el mensaje sea el mismo en los dos casos, algo como
     "El correo o la clave no son correctos". Si distingues entre "no existe" y
     "clave incorrecta", le estas diciendo a cualquiera que correos estan
     registrados.

     El password_hash NUNCA debe ir en la respuesta.


3.2  POST /api/v1/auth/register

     recibe:
       { "tenant_id": "...", "nombre": "...", "email": "...",
         "password": "...", "rol": "cajero" }

     responde 201 con la misma forma que el login (token + usuario), asi la
     persona queda dentro al terminar de crear la cuenta.

     409 si el correo ya existe en ese tenant (tienes el UNIQUE que lo detecta).
     400 si falta algun campo o la clave es muy corta.

     De mi lado valido que la clave tenga al menos 8 caracteres y que las dos
     escrituras coincidan, pero eso es solo ayuda visual. La validacion que vale
     es la tuya, porque cualquiera puede llamar la API sin pasar por mi pantalla.

     La clave se guarda con bcrypt, nunca en texto plano.


3.3  GET /api/v1/auth/me

     Lee el token de la cabecera Authorization y devuelve el usuario.
     Lo uso al arrancar para saber si la sesion guardada sigue viva.

     responde 200: { "success": true, "data": { "usuario": { ... } } }
     401 si el token vencio, es invalido o no viene.

No necesito endpoint de logout. El JWT no se guarda en el servidor, asi que
cerrar sesion es borrar el token en el navegador, y eso ya lo hago. Si mas
adelante quieres revocar tokens, lo conversamos.

--------------------------------------------------------------------------------
5. ARREGLAR EL USUARIO SEMBRADO
--------------------------------------------------------------------------------

En init-db.ts, lineas 81 (SQLite) y 286 (PostgreSQL), el usuario demo se siembra
asi:

    '$2b$10$demoHashPasswordForAdminDemoUser2026'

Eso no es un hash bcrypt, es texto que lo parece. Tiene 43 caracteres y un
bcrypt real tiene 60, asi que ninguna clave va a coincidir nunca.

Hay que generarlo de verdad con bcrypt.hash() y, de paso, sembrar tambien un
usuario con rol cajero, porque hoy solo existe el admin.

Cuando los siembres, pasame los dos correos y las dos claves para poder probar.


--------------------------------------------------------------------------------
6. LO QUE EL FRONTEND YA HACE
--------------------------------------------------------------------------------

- Manda Authorization: Bearer <token> en todas las peticiones.
- Si cualquier endpoint responde 401, cierra la sesion y vuelve al login solo.
  Asi que cuando pongas el JWT con vencimiento ya queda manejado.
- Guarda la sesion en el navegador para no pedir la clave en cada recarga.
- Al cerrar sesion limpia tambien la cache de datos, para que el siguiente
  usuario no alcance a ver nada del anterior.
- Pantallas: login, registro con seleccion de rol, y boton de salir en el menu.

Reparto de pantallas que quedo:

    Cajero (6):  Caja, Notificaciones, Inventario, Cierre de Caja,
                 Historial de Ventas y Configuracion.
    Admin (11):  las anteriores mas Panel General, Facturas, Proveedores,
                 Reposicion de Stock y Respaldo de Facturas.

Configuracion la ven los dos, pero el cajero solo alcanza la parte de apariencia
(tema y modo de interfaz). Las reglas del negocio se muestran solo al admin.


--------------------------------------------------------------------------------
7. COMO LO ENCENDEMOS
--------------------------------------------------------------------------------

Deje una llave en el .env del frontend:

    VITE_AUTH_ACTIVA=false

Con false la app funciona como siempre y el login se puede revisar entrando a
/login. Cuando tengas los tres endpoints la pongo en true y ahi empieza a pedir
sesion de verdad.

Ya lo probe con la llave encendida: sin sesion redirige al login, un cajero que
escribe /configuracion ve lo que le corresponde, y el boton de salir limpia todo.
