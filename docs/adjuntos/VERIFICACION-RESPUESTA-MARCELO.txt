NO FUNCIONA - los 4 endpoints nuevos devuelven HTTP 500
--------------------------------------------------------------------------------

Los probe uno por uno contra el backend levantado con SQLite. Ninguno completa.
La causa en casi todos es la misma: la tabla historial_stock tiene un CHECK que
solo acepta tres valores.

    CREATE TABLE historial_stock (
      ...
      tipo_movimiento TEXT NOT NULL
        CHECK (tipo_movimiento IN ('venta', 'ingreso_factura', 'ajuste')),
      ...
    )


A)  POST /api/v1/pos/products  ->  500

    Error: CHECK constraint failed: tipo_movimiento IN ('venta','ingreso_factura','ajuste')
    Causa: pos.routes.ts linea 112 inserta 'alta_inicial', que no esta permitido.
    Solo falla si stock_actual > 0, porque el INSERT a historial_stock esta
    dentro de ese if.

    OJO, esto es lo peor del caso: el producto SI queda creado. El INSERT a
    productos corre antes y no hay transaccion que lo revierta. El frontend
    recibe un 500, el usuario reintenta y termina con productos duplicados.


B)  PUT /api/v1/pos/products/:id  ->  500

    Error: "Provided value cannot be bound to SQLite parameter 1."
    Lo probe mandando solo dos campos (precio_venta y lote). Parece que los
    campos que no van en el body llegan como undefined a los binds del COALESCE,
    y node:sqlite no acepta undefined (hay que pasar null).


C)  PATCH /api/v1/pos/products/:id/stock  ->  500

    Causa: pos.routes.ts linea ~329 inserta 'ajuste_manual'.
    El CHECK permite 'ajuste', no 'ajuste_manual'.


D)  POST /api/v1/pos/mermas  ->  500

    Error: no such column: "now" - should this be a string literal in single-quotes?
    Causa: la consulta usa now(), que es sintaxis de PostgreSQL. En SQLite va
    datetime('now').
    Ademas inserta tipo_movimiento = 'merma', que tampoco esta en el CHECK, asi
    que al arreglar el now() va a fallar igual por la constraint.

    Mismo problema que en A: la fila SI queda escrita en la tabla mermas antes
    de que falle el historial. Lo verifique, tuve que borrarla a mano.


Para arreglarlo hay dos caminos: ampliar el CHECK de historial_stock para que
acepte 'alta_inicial', 'ajuste_manual' y 'merma', o usar los valores que ya
existen. Y en los cuatro casos conviene envolver las escrituras en una
transaccion para que un fallo no deje datos a medias.
